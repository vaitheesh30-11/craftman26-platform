# 1. Enterprise Memory Hierarchy

Sentinel-IQ does **not** rely on a single vector database or a single memory abstraction.

Instead, it separates memory into four independent cognitive layers.

Each layer has one responsibility only.

This separation prevents:

- Context window overflow
- State corruption
- Hallucinated reasoning
- Non-deterministic execution
- Hidden side effects between agents

The memory hierarchy follows this architecture.

```mermaid
flowchart TD

WM["Tier 1<br/>Working Memory<br/>LangGraph State Tensor"]

GM["Tier 2<br/>Graph Memory<br/>Amazon Neptune"]

VM["Tier 3<br/>Vector Memory<br/>OpenSearch Serverless"]

PM["Tier 4<br/>Procedural Memory<br/>Deterministic AWS Tools"]

WM --> GM
GM --> VM
VM --> PM
```

---

## Why Four Memory Layers?

Large enterprise AI systems fail when every piece of information is stored in the same place.

For example,

- policy JSON
- CloudTrail logs
- IAM trust relationships
- PagerDuty incidents
- execution state

all have completely different lifecycles.

Keeping them together causes:

- duplicated information
- stale context
- exploding token usage
- inconsistent reasoning

Instead, Sentinel-IQ assigns each type of information to the correct memory layer.

| Tier | Memory | Responsibility |
|------|----------|----------------|
| 1 | Working Memory | Current execution state |
| 2 | Graph Memory | Enterprise topology |
| 3 | Vector Memory | Historical semantic knowledge |
| 4 | Procedural Memory | Deterministic execution |

# 2. Tier 1 – Working Memory State Tensor

Working Memory is the **only mutable memory** inside the execution engine.

Every LangGraph node receives exactly the same state object.

Each node performs three actions:

1. Read State
2. Update State
3. Return State

No node owns private mutable memory.

This guarantees deterministic execution.

---

## Responsibilities

Working Memory stores only information required during the current execution.

Examples include:

- current policy AST
- verification status
- blast radius
- execution metadata
- debate history
- retry count
- temporary TTL values

Once execution completes, Working Memory is destroyed.

It is **never persisted**.

### 3. Target Layer

Defines the resource currently being evaluated.

Examples include:

- AWS Account

### 4. Debate Layer

An append-only reasoning history.

Every agent appends reasoning instead of modifying previous entries.

Benefits include:

- auditability

- deterministic history

---

### 5. Policy Layer

Contains:

- Original Policy

- Byte Count

The original policy is immutable.

Only the working copy changes.

### 6. Verification Layer

Contains formal proof artifacts.

Examples include:

- Zelkova proof
- SMT status

- blast radius
- impacted services
- trust chain analysis

---

### 7. Lifecycle Layer

Tracks temporary execution metadata.

Examples include:

- TTL expiration
- Break-glass duration
- Approval state
- Rollback token

# Why Working Memory Is Not a Database

Working Memory should never become long-term storage.

It exists only to coordinate the current execution.

Long-term persistence belongs elsewhere.

| Information | Stored In |
|------------|-----------|
| Current AST | Working Memory |
| CloudTrail History | Athena |
| IAM Graph | Neptune |
| Incident History | OpenSearch |
| Policies | AWS Organizations |
| Verification Reports | S3 |

# 3. Tier 2 – Topological Graph Memory

Enterprise authorization is inherently a graph problem.

Questions such as:

- Who can access Production?
- Which vendor can reach KMS?
- Which SCP affects this account?
- Which role can assume another role?

cannot be answered efficiently using vector search or relational joins.

Instead, Sentinel-IQ models AWS as a property graph.

Amazon Neptune provides this capability.

## Graph Relationships

Graph relationships define how identities, policies, resources, and organizational units are connected. These relationships enable the reasoning engine to perform graph traversals, blast-radius analysis, and trust validation.

### Core Relationship Types

| Relationship | Source | Target | Purpose |
|--------------|--------|--------|---------|
| `PARENT_OF` | OU | OU | Represents AWS Organization hierarchy |
| `CONTAINS_ACCOUNT` | OU | AWS Account | Maps accounts to Organizational Units |
| `BOUNDED_BY` | OU / Account | SCP Policy | Indicates which SCP governs the target |
| `ASSUMES_ROLE` | IAM Role | IAM Role | Cross-account trust relationship |
| `CAN_ACCESS` | IAM Role | AWS Resource | Effective permissions after evaluation |
| `MEMBER_OF` | IAM User | IAM Group | Group membership |
| `ATTACHED_POLICY` | IAM Role | IAM Policy | Attached managed/inline policy |
| `OWNS_RESOURCE` | AWS Account | AWS Resource | Ownership mapping |

---

## Relationship Metadata

Relationships are not simple connections.

Each edge stores metadata required for security reasoning.

### Example

```json
{
  "relationship": "ASSUMES_ROLE",
  "source_role": "VendorRole",
  "target_role": "ProdDeployRole",
  "has_external_id": true,
  "has_source_arn": false,
  "has_source_account": true,
  "created_at": "2026-07-17T10:15:30Z"
}
```

This metadata allows the Graph Traversal Agent to detect insecure trust relationships instead of merely discovering connectivity.

---

## Graph Traversal Strategy

Sentinel-IQ never performs unrestricted graph traversals.

Traversal depth is constrained to reduce computational cost and eliminate irrelevant paths.

| Traversal | Maximum Depth | Purpose |
|------------|--------------|---------|
| SCP Inheritance | Root → Account | Policy evaluation |
| AssumeRole | 5 Hops | Confused Deputy detection |
| Blast Radius | 7 Hops | Authorization impact analysis |
| Resource Reachability | 4 Hops | Exposure analysis |

---

## Example: Detecting a Confused Deputy

```text
VendorRole
    │
    ▼
SharedServicesRole
    │
    ▼
AutomationRole
    │
    ▼
ProductionDeployRole
    │
    ▼
KMSKey
```

The traversal engine evaluates every edge.

If any `ASSUMES_ROLE` edge lacks:

- `aws:SourceArn`
- `aws:SourceAccount`
- `ExternalId`

the chain is flagged as vulnerable.

---

## SCP Inheritance Resolution

The graph engine reconstructs the effective SCP boundary by traversing upward.

```text
Root
 │
 ├── Security OU
 │
 ├── Platform OU
 │
 ├── Application OU
 │
 └── Production Account
```

Each attached SCP is collected.

The authorization engine evaluates the final SCP set in inheritance order.

# 4. Tier 3 – Episodic Vector Memory

Graph Memory explains **how infrastructure is connected**.

Vector Memory explains **what has happened before**.

It provides historical operational context that cannot be represented as graph relationships.

Examples include:

- PagerDuty incidents
- Jira tickets
- Security investigations
- Architecture decisions
- Compliance documentation
- Production runbooks
- Previous approvals
- Root Cause Analyses

---

## Why Vector Memory Exists

Consider a break-glass request.

The request states:

> "Production deployment is blocked due to KMS permissions."

Without historical context, an LLM cannot determine whether this request is legitimate.

Vector Memory answers questions such as:

- Has this happened before?
- Was it previously approved?
- Is there an active Sev-1 incident?
- Which runbook applies?
- Who approved similar requests?

# 5. Tier 4 – Procedural Memory

Procedural Memory is fundamentally different from Graph Memory and Vector Memory.

It stores **capabilities**, not **knowledge**.

An LLM should never:

- calculate policy byte counts
- decode STS authorization messages
- execute graph traversals
- run formal verification
- simulate IAM authorization

Instead, it delegates those responsibilities to deterministic tools.

---

## Why Deterministic Tools?

Enterprise governance requires reproducible behavior.

The same input must always produce the same output.

LLMs cannot guarantee deterministic execution for arithmetic, parsing, or policy evaluation.

Therefore, Sentinel-IQ separates reasoning from execution.

```mermaid
flowchart LR

LLM["Reasoning Agent"]

TOOLS["Deterministic Tool Registry"]

AWS["AWS APIs"]

LLM --> TOOLS

TOOLS --> AWS
```

---

## Tool Registry Overview

| Tool | Responsibility |
|------|----------------|
| AST Compiler | Policy parsing and optimization |
| SLR Exemption Tool | Prevent AWS service lockouts |
| Zelkova Verifier | Formal mathematical verification |
| STS Decoder | Decode AccessDenied authorization messages |
| Neptune GraphRAG | Trust graph traversal |
| Chronos TTL | Automatic temporary access revocation |

---

## Execution Philosophy

The LLM is responsible for:

- planning
- reasoning
- orchestration
- decision making

The tools are responsible for:

- execution
- validation
- parsing
- simulation
- AWS interactions

This strict separation ensures production-grade reliability, repeatability, and auditability.

# 6. Multi-Agent Coalition Architecture

Sentinel-IQ is not implemented as a single monolithic AI agent.

Instead, it is composed of specialized cognitive coalitions, where each coalition owns one responsibility within the governance lifecycle.

This architecture follows the same principle used in distributed systems:

> **Specialization produces more reliable systems than generalization.**

Each coalition has deterministic responsibilities, bounded context, dedicated tools, and explicit contracts.

# Why Multiple Coalitions?

Enterprise governance problems belong to different domains.

For example,

An SCP optimization problem requires:

- AST manipulation
- byte optimization
- policy rewriting

A trust policy problem requires:

- graph traversal
- IAM reasoning
- transitive trust analysis

A break-glass request requires:

- historical incidents
- PagerDuty context
- operational validation

Trying to solve all three with one prompt produces:

- prompt bloat
- hallucinations
- inconsistent outputs
- excessive token usage

Instead, Sentinel-IQ routes each problem to a dedicated coalition.

## Step 1 — AST Compilation

The raw SCP JSON is parsed into an Abstract Syntax Tree.

The AST enables structural manipulation rather than string replacement.

Benefits include:

- deterministic edits
- duplicate detection
- condition normalization
- statement merging

---

## Step 2 — Statement Aggregation

Duplicate statements are merged.

Example

Before

```
ec2:StartInstances

ec2:StopInstances

ec2:DescribeInstances
```

After

```
ec2:*Instances
```

This dramatically reduces SCP size.

---

## Step 3 — SLR Protection

Broad deny statements frequently break AWS-managed services.

The SLR Injector scans for these cases.

Example

Instead of:

```
Deny kms:*
```

the engine injects

```json
{
  "Condition": {
    "Bool": {
      "aws:PrincipalIsAWSService": "true"
    }
  }
}
```

This preserves AWS Backup, Macie, Config, GuardDuty, and other managed services.

---

## Step 4 — Byte Optimization

The optimized policy is measured.

Maximum SCP size

```
10,240 bytes
```

If exceeded,

the compiler automatically partitions the SCP into Parent and Child organizational policies.

Simulation predicts behavior.

Formal Verification proves behavior.

Sentinel-IQ uses AWS Access Analyzer's Zelkova reasoning engine.

Instead of asking

> "Will this probably work?"

it asks

> "Can AWS mathematically prove this policy is safe?"

---

## Verification Pipeline

```mermaid
flowchart TD

BASELINE[Existing Policy]

CANDIDATE[Candidate Policy]

ZELKOVA[AWS Zelkova]

COMPARE[Automated Reasoning]

RESULT[Formal Proof]

BASELINE --> ZELKOVA

CANDIDATE --> ZELKOVA

ZELKOVA --> COMPARE

COMPARE --> RESULT
```

Possible outputs

| Status | Meaning |
|----------|---------|
| PASS | Safe |
| FAIL_PRIVILEGE_ESCALATION | New permissions introduced |
| FAIL_SYNTAX | Invalid policy |
| UNVERIFIED | Unable to prove |

# Self-Correction Debate Loop

One of the most important features of Sentinel-IQ is that failure does **not** immediately terminate execution.

Instead,

verification failures trigger an autonomous correction cycle.

```mermaid
flowchart TD

A[Candidate Policy]

B[Zelkova Verification]

C{PASS?}

D[Deployment]

E[Counter Example]

F[Append Debate Log]

G[Coalition Alpha]

A --> B

B --> C

C -->|YES| D

C -->|NO| E

E --> F

F --> G

G --> A
```

This creates an iterative refinement process.

Each loop produces a better candidate policy.

---

# Debate Memory

Every failed verification appends structured feedback.

Example

```json
{
  "iteration": 2,
  "agent": "Beta",
  "reason": "Privilege escalation detected",
  "resource": "arn:aws:s3:::production-bucket",
  "recommendation": "Restrict wildcard action"
}
```

Coalition Alpha receives this feedback during the next iteration.

No reasoning is lost.

# Retry Limits

Infinite loops are unacceptable in production.

Therefore,

Sentinel-IQ enforces a strict retry policy.

| Attempt | Action |
|----------|---------|
| 1 | Retry automatically |
| 2 | Retry automatically |
| 3 | Final retry |
| >3 | Escalate to Human Approval |

Maximum retries

```
3
```

This prevents runaway execution costs.

# Production Design Principles

The execution engine follows several architectural principles.

1. Every action is deterministic.
2. Every state transition is auditable.
3. Every policy is formally verified.
4. Every deployment is reversible.
5. Every retry is bounded.
6. Every approval is explicit.
7. Every temporary permission has an expiration.
8. Every reasoning step is preserved in Working Memory.
9. Every coalition has a single responsibility.
10. Every production change is explainable.

These principles ensure Sentinel-IQ remains predictable, secure, scalable, and suitable for enterprise governance environments.
