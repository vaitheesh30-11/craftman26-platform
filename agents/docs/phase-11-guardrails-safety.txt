PHASE 11 — Guardrails & Safety Substrate
========================================

Owner assumption: one principal engineer. Duration: 2 days.

1. Objective
------------
Provision the safety primitives every specialist depends on: the published Bedrock Guardrail, the XML fencer + sanitizer, the Zelkova pre/post-check adapter, and the two-signer break-glass path for Sentinel's own resources. This phase is a prerequisite for phase-01 and beyond.

2. Deliverables
---------------
- Bedrock Guardrail `IAMSentinelGuardrail-v1` (CDK custom resource).
- XML fencer utility in `adapters/prompts/xml_fencer.py`.
- Sanitizer utility in `adapters/prompts/sanitizer.py`.
- Zelkova adapter in `adapters/zelkova/client.py`.
- Break-glass STS provisioning in `aws-infra/lib/security_stack.py`.
- Prompt-injection corpus at `agents/tests/prompt_injection/corpus.jsonl` (200 payloads).

3. Interface Contracts
----------------------
```python
class UntrustedBlock(Base):
    type: str
    body: str

class FencedPrompt(Base):
    trusted_input_json: str                # canonicalized JSON string
    untrusted_blocks: list[UntrustedBlock]
    composed_text: str                     # final prompt with fences

class ZelkovaWitness(Base):
    principal_arn: Optional[str]
    action: str
    resource: str
    context: dict[str, str]

class ZelkovaResult(Base):
    pass_: bool = Field(alias="pass")
    witness: Optional[ZelkovaWitness] = None
    raw_response: dict[str, object]
    latency_ms: int
    invoked_at: AwareDatetime
```

4. Implementation Steps
-----------------------
Step 1 — Sanitizer (`adapters/prompts/sanitizer.py`).
  - `sanitize_untrusted(value: str, *, max_length: int = 4096) -> str`:
    1. Unicode NFKC normalize.
    2. Strip characters whose Unicode category starts with `C` (control).
    3. Remove `<`, `>`, backtick.
    4. Collapse whitespace runs to single space.
    5. Truncate to `max_length`.
    6. If the truncated string matches any forbidden pattern (see §5), raise `SanitizerRejection`.
  - Property test: after sanitization, no forbidden pattern is present, no `<` or `>` remains.

Step 2 — XML fencer (`adapters/prompts/xml_fencer.py`).
  - `build_prompt(trusted_input: dict, blocks: list[UntrustedBlock]) -> str`:
    1. Serialize `trusted_input` via JCS (RFC 8785) — deterministic, no whitespace.
    2. Wrap in `<trusted_input>…</trusted_input>`.
    3. For each block, sanitize `block.body`, wrap in `<untrusted_context type="{block.type}">…</untrusted_context>`.
    4. Concatenate; return.
  - Never accept a `type` containing anything other than `[a-z_]+`; anything else raises.

Step 3 — Guardrail configuration.
  - CDK custom resource that calls `bedrock:CreateGuardrail`:

  - Guardrail id and version stored in SSM parameters `/sentinel/guardrail/id` and `/sentinel/guardrail/version`.

Step 4 — Zelkova adapter (`adapters/zelkova/client.py`).
  - `check_no_new_access(existing_policy: dict, new_policy: dict, *, policy_type: str = "IDENTITY_POLICY") -> ZelkovaResult`:
    1. Call `access-analyzer:CheckNoNewAccess` with the two policies and `policyType`.
    2. On throttling: exp backoff 200/500/2000 ms, max 3 attempts.
    3. On unrecoverable error: raise `ZelkovaError`. NEVER return `pass_=True` on error.
    4. Emit signed evidence blob capturing input policies + response.
    5. Return `ZelkovaResult`.
  - `check_post_apply(role_arn: str, expected_policy: dict, *, wait_seconds: int = 15, max_polls: int = 3)`:
    1. Sleep `wait_seconds`, then `iam:GetRolePolicy` → observed_policy.
    2. Compare hash of canonicalized observed vs expected.
    3. If mismatch, poll up to `max_polls` times.
    4. Return `ZelkovaResult` (pass_=True only when observed matches expected AND `CheckNoNewAccess(baseline=expected, candidate=observed).pass_ is True`).

Step 5 — Break-glass STS.
  - IAM role `IAMSentinelBreakGlassRole` with:
    - Trust: only humans with `IAMSentinelBreakGlassInitiator` group.
    - Session tag requirement: `BreakGlass=IAMSentinel-Two-Signer`.
    - Permissions boundary: `IAMSentinelBreakGlassBoundary` restricting to Sentinel resources only (specific ARN allow-list of DDB tables, S3 buckets, KMS keys, Bedrock agents/guardrails).
  - Alarm: CloudTrail rule on any use of the role → SNS to a security-approver group.
  - Session TTL: 900 s (15 min). Two-signer: session-tag issuance requires an approver role from a second person (implemented via a small Step Functions state machine that requires two `sts:AssumeRole` events within a 60-s window from two distinct principals).

Step 6 — Prompt-injection corpus.
  - 200 payloads covering: direct instruction override, indirect via untrusted context, role names as instructions, base64-encoded overrides, homoglyph attacks, RTL-override attacks, XML-tag closure attempts, JSON injection.
  - Each payload has: `payload`, `expected_outcome` (`sanitizer_reject` | `guardrail_intervened` | `refusal`), `feature_id_scope`.
  - Corpus is regenerated quarterly with fresh community-sourced payloads.

5. Forbidden Patterns
---------------------
Enforced by the sanitizer:
- `</trusted_input`
- `</untrusted_context`
- `</system`
- `human\s*:` (case-insensitive)
- `assistant\s*:`
- `ignore\s+(the\s+)?(previous|above|prior)\s+instructions`
- `you\s+are\s+now\s+`
- `disregard\s+`
- `override\s+`
- `<\|.*?\|>` (fake control tokens)

Match hits raise `SanitizerRejection`. Callers translate to `SpecialistVerdict(verdict="INCONCLUSIVE", reason="input rejected by sanitizer")`.

6. IAM Policy
-------------
Custom-resource role for Guardrail creation: `bedrock:CreateGuardrail`, `UpdateGuardrail`, `DeleteGuardrail`, `CreateGuardrailVersion`, `ListGuardrails`, `GetGuardrail`. Resource `*` (Guardrail ARN is generated by AWS).

Zelkova client role: `access-analyzer:CheckNoNewAccess` (Resource `*` — API surface). Documented inline.

Break-glass role: least-privilege on Sentinel resources per §Step 5.

7. Test Plan
------------
- Sanitizer property tests: 1,000 Hypothesis examples per rule; verify no forbidden pattern survives.
- XML fencer: composition + deterministic output; snapshot test.
- Zelkova: moto `access-analyzer` responses; verify never-fail-open under error.
- Guardrail deployment: `cdk deploy` on a scratch account; verify guardrail exists and passes canary probe (an input containing "ignore your instructions" is denied).
- Break-glass: end-to-end with two synthetic principals; verify without the second signer the STS AssumeRole fails.
- Corpus: run all 200 payloads through Prime dev alias; verify every payload matches its expected outcome.

8. Acceptance Criteria
----------------------
- [ ] Sanitizer property tests pass 10,000 examples with zero counterexamples.
- [ ] Zero payloads in the 200-corpus follow through the model.
- [ ] Zelkova adapter never returns `pass_=True` on ANY error path (property test).
- [ ] Break-glass single-signer attempt fails; two-signer succeeds; every use emits an alarm.
- [ ] Guardrail canary probe passes on every deploy.

9. Risks & Mitigations
-----------------------
Risk: Guardrail overblocks legitimate queries (false positives on `12-digit account ids` in normal usage).
  Mitigation: `ANONYMIZE` (not BLOCK) for account IDs; measure block rate weekly; adjust content-filter strengths only after 30 days of data.

Risk: Zelkova adapter latency spikes.
  Mitigation: p95 SLO 3 s; if breached, alarm and page. Prime is instructed to escalate on Zelkova timeout, never fail-open.

Risk: injection corpus staleness.
  Mitigation: quarterly refresh + `garak`-style automated variant generation from a base set.
