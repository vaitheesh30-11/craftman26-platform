## 3. Zero-Trust Privilege Separation Model

The architecture enforces an absolute boundary between the **Reasoning Plane (Agents)** and the **Execution Plane (Mutator Engine)**. Reasoning agents are physically unable to perform state-changing operations on AWS infrastructure.

│  └───────────────────┘       └───────────────────┘       └─────────────┬─────────────┘   │

### 3.1 Reasoning Plane Permission Rules
* **Strict Read-Only Enforcement:** Agent execution roles are provisioned with read-only permissions targeting AWS Organizations, IAM metadata, Access Analyzer, and STS Decode tools.
* **Explicit Mutation Denies:** A global `Deny` statement explicitly blocks all `UpdatePolicy`, `CreatePolicy`, `AttachPolicy`, and `PutRolePolicy` actions across all AWS resources for the agent execution role.

### 3.2 Execution Plane Permission Rules
* **Isolated Execution Lambda:** Infrastructure mutation logic is encapsulated in an isolated Lambda function invoked exclusively by the control plane upon receiving a validated HITL approval signal.
* **Scoped Write Credentials:** The Executor Lambda possesses scoped permissions restricted to targeted Organizational Units (OUs) and IAM role paths.

## 4. Multi-Layer Prompt Injection Defense Architecture

Untrusted data ingested from external enterprise sources (AWS Resource Tags, User Descriptions, Jira Tickets, CloudTrail Logs) must pass through a multi-tier sanitization pipeline before reaching LLM reasoning contexts.


```

[Raw External Ingress Payload]
(AWS Tags / CloudTrail / Jira / Slack)
│
▼
┌──────────────────────────────────────────────┐
│ TIER 1: PARSER-LEVEL SANITIZATION            │
│ - Strips control characters                  │
│ - Removes embedded XML/HTML closing tags     │
└──────────────────────┬───────────────────────┘
│
▼
┌──────────────────────────────────────────────┐
│ TIER 2: STRUCTURAL XML FENCING               │
│ - Encloses payload in <untrusted_context>    │
│ - Injects system prompt parser rules         │
└──────────────────────┬───────────────────────┘
│
▼
┌──────────────────────────────────────────────┐
│ TIER 3: AST SCHEMA STRUCTURAL GATE           │
│ - Validates policy JSON AST structural rules │
│ - Rejects unrecognized keys or properties    │
└──────────────────────────────────────────────┘

```

### 4.1 Structural XML Fencing Protocol
1. **Context Tag Isolation:** All dynamic untrusted strings are enclosed within `<untrusted_context>` tags in LLM prompts.
2. **System Prompt Isolation Directives:** System prompts instruct the LLM that any text contained within `<untrusted_context>` must be treated as passive string data and never interpreted as system instructions, roleplay requests, or operational commands.
3. **Closing-Tag Neutralization:** Input pre-processors strip any literal occurrences of `</untrusted_context>` from input payloads to prevent prompt injection escape attacks.

## 5. Mathematical & Policy Circuit Breakers (Zero-Bypass Gates)

To guarantee that non-deterministic LLM behavior cannot compromise enterprise security, the architecture implements three deterministic, non-bypassable circuit breakers.

### Gate 1: AST Structural & Character Limit Gate
* **Enforcement:** Evaluates policy AST length and syntax immediately following Coalition Alpha synthesis.
* **Rules:**
  * Must parse cleanly as single-object JSON.
  * Serialized byte size must be $\le 10,240$ bytes.
  * Statement block must not contain conflicting `Allow` and `Deny` actions for identical resource ARNs.

### Gate 2: Zelkova SMT Mathematical Proof Gate
* **Enforcement:** Invokes AWS Access Analyzer `check_no_new_access` SMT solver during Coalition Beta evaluation.
* **Rules:**
  * Must return a result status of `PASS`.
  * Counter-example array must be empty.
  * Any `FAIL_PRIVILEGE_ESCALATION` result halts execution and triggers a self-correction loop or HITL escalation.

### Gate 3: Service-Linked Role (SLR) Protection Gate
* **Enforcement:** Scans proposed policies for broad deny conditions targeting AWS-managed services.
* **Rules:**
  * Broad `Deny` statements (e.g., `s3:*`, `kms:*`) must contain explicit `aws:PrincipalIsAWSService` condition blocks to prevent accidental lockout of AWS Backup, Macie, or GuardDuty.

## 6. Denial-of-Wallet & Infinite Loop Mitigations

Self-correction debate loops between Coalition Alpha and Coalition Beta are bounded to prevent resource exhaustion and runaway LLM API costs.

### Control Mechanisms
1. **Loop Count Cap:** The `loop_count` state variable increments on every iteration. Execution is capped at a maximum of **3 turns**.
2. **Degraded Escalation Mode:** If iteration 3 fails Zelkova verification, the engine terminates the debate loop, sets a `SECURITY_WARNING` flag, attaches the SMT counter-examples, and routes the state directly to `AWAITING_HITL` for manual human intervention.
3. **Session Token Ceiling:** A hard token-budget ceiling is tracked per session. Exceeding the budget triggers an immediate session abort and alerts the platform team.

## 7. Cryptographic Non-Repudiation & WORM Audit Trail Specification

To satisfy SEC Rule 17a-4, SOC2 Type II, HIPAA, and ISO27001 compliance standards, every execution session generates an immutable, cryptographically verifiable audit trail.


```

[WorkingMemoryState Tensor]
│
▼
┌──────────────────────────────────────────────┐
│ SHA-256 STATE DIGEST GENERATION              │
│ Computes cryptographic hash over complete    │
│ state, debate log, SMT proofs, and diffs.    │
└──────────────────────┬───────────────────────┘
│
▼
┌──────────────────────────────────────────────┐
│ S3 OBJECT LOCK COMPLIANCE ARCHIVE            │
│ Writes audit record to Amazon S3 WORM bucket │
│ with Compliance Mode retention enabled.      │
└──────────────────────────────────────────────┘

```

### Audit Record Requirements
* **Audit Payload Contents:** Complete `WorkingMemoryState` execution tensor, raw input triggers, agent debate logs, Zelkova SMT proof outputs, blast radius metrics, operator approval signals (including approver IAM ARN and timestamp), and final deployed policy diffs.
* **Storage Target:** Amazon S3 Bucket configured with **Object Lock in Compliance Mode**. Records cannot be deleted, overwritten, or altered by any user, including root account administrators, until the retention period expires.
* **Cryptographic Verification:** State digests are generated using SHA-256 hashes over the serialized JSON state tensor, providing non-repudiation during enterprise compliance audits.
